1. CURRENT HOSTED STATE (from code)
- api/index.py subclasses server.app.Handler: CLOUD=True, any Host, same-host Origin for writes,
  Secure cookie, Postgres required, MAX_BODY = 4 MiB, no-store on every response.
- It never calls api_archivos.configurar_almacen(). Hosted upload, download, complete and
  reprocess therefore answer 503 almacen_no_configurado. Metadata and listing routes work.
- configurar_archivos() runs only in serve() (local) and deliberately wires nothing for Postgres.
- vercel.json: git deployments disabled, static output "web", one function, maxDuration 120.
  Routing is hash-based, so no SPA rewrite is needed.
- Sessions, login throttling, upload leases and the 5-pending limit are all database rows; nothing
  depends on process memory except the lazily built store object, which is safe per instance.

2. MINIMAL ADAPTER / CONFIGURATION GAPS (A-owned unless noted)
G1 Store injection in the hosted entry point: one configurar_almacen(factory) call at import,
   fail-closed (no factory -> existing 503). No route or handler change.
G2 Configuration names for the store (B proposes, A reads them in the entry point). Today only
   ARA_MAP_ARCHIVOS exists and it means a local directory.
G3 Size limits are inconsistent in the cloud: adapter 4 MiB; /api/config maxUploadBytes 4 MiB
   (used only by Excel import); web/lib/archivos.js LIMITE_BYTES hard-codes 25/20 MiB and the
   detail text says "Máximo 25 MB". A hosted user would be invited to upload 25 MB and get 413.
   Fixing the client side touches B-owned files.
G4 If the route is a long-running host: a hosted entry point is missing. serve() binds 127.0.0.1,
   opens a browser, and Handler rejects non-loopback Host. The cloud subclass already has the
   right policy; it needs a server loop bound for a TLS reverse proxy. Small, A-owned.
G5 No hosted test covers attachments: tests/test_cloud.py (11 tests) has no store case.
G6 Every database session takes one workspace advisory lock (30 s wait, then "busy"). Store I/O
   and KMZ parsing run outside sessions, so large transfers do not hold it, but all requests
   still serialize on it. Acceptable for a small private portal; should be measured, not assumed.

3. ATTACHMENT TRANSFER COMPATIBILITY
- Upload: one PUT of the raw file, Content-Length required, no chunking or resume; body fully
  buffered. Limits PDF 25 MiB, KMZ 20 MiB.
- Download: one response with the whole file, buffered and SHA-256 verified server-side first,
  then verified again in the browser.
- Geometry: 512 KiB slices, metadata responses capped at 128 KiB. Fits any route.
- Table/detail JSON: paged. Fits any route.
Consequence by route:
  Route V (Vercel function + Neon + object store): uploads and downloads above ~4 MiB cannot pass
    through the function. Either (a) cap attachments at 4 MiB for the portal — needs G1-G3 only —
    or (b) add a direct browser-to-store transfer protocol, which is new design for both teams
    (authorization, hash verification, expiry) and conflicts with the current "bytes only through
    authorized handlers" model. (b) is not minimal.
  Route H (one private long-running host + persistent volume, Postgres local or Neon): the
    existing 25/20 MiB flow works unchanged. The accepted AlmacenLocal is sufficient as the byte
    layer; B adds backup/recovery of the volume. Needs G1/G4 only.
Peak memory per large transfer is roughly 2x file size (body plus verification buffer).
