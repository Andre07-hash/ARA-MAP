2. COMPLETION AND RETRIES
Sequence unchanged: scope -> lease 180 s -> new final/<version>/<nonce> -> build final ->
verify the FINAL object (size, SHA-256, signature) -> bounded KMZ parse -> one write
transaction (reverify, lease owned, pointer/history/outcome). Store and parser I/O stay
outside write transactions. Only "build final" differs: compose parts 0..P-1 into the nonce
with a no-overwrite write [B-TEXT: Almacen method name and uncertain-write signalling].
Lost part response: resend. Missing part: 409 contenido_temporal_ausente, retry in deadline.
Lost completion response: replay. Two completions: one lease. Killed function: lease expires.
Uncertain final write or uncertain commit: the object is kept and reported
(limpieza_pendiente); deletion only of this attempt's own nonce after the database proves it
unreferenced. No sweep.
Upload deadline passed (409 subida_expirada): the version still counts as pending until the
60-minute limit, so the client cancels it and starts again with a FRESH Idempotency-Key
(the old key would replay the expired version). New version, new staging key.
Deadlines 15/60 min, lease 180 s, 5 pending: unchanged.

3. DOWNLOAD (supervisor's recommendation adopted; no alternative proposed)
Each GET …/descarga?desde=O: full reauthorization (session, archivos.ver, current scope,
version disponible) -> read the whole final object -> verify size and SHA-256 against the
database row -> return bytes [O, O+3 MiB) of that verified buffer. No lectura value, no
registry, no token, no ranged store read.
Headers: application/octet-stream, "private, no-store", CSP sandbox, nosniff,
X-Archivo-Version-Id, X-Archivo-Sha256, X-Archivo-Tamano, X-Archivo-Desde,
X-Archivo-Longitud, X-Archivo-Siguiente (offset or "fin").
Errors: 400 desplazamiento_invalido (malformed or O >= size); 503 contenido_no_disponible;
503 objeto_final_inconsistente; 503 almacen_no_disponible.
Browser keeps complete-file size/SHA-256 verification before offering the file.
Disclosed cost: every slice reads the full object. 25 MiB PDF = 9 reads = 225 MiB from the
store per download; 20 MiB KMZ = 7 reads = 140 MiB; about 25 MiB buffered per invocation.
Goes into the hosted timing/cost check.
Cloud adapter guard (A): a binary response above 4 MiB is refused and logged, never sent.

Logs: condition class, exception type, variable NAMES. Never messages, tokens, ARNs with
account ids, keys or URLs. All of these occur after application authorization, so they
cannot reveal a resource to someone without access.
Variables (names for B to confirm): ARA_MAP_ALMACEN=s3, ARA_MAP_S3_BUCKET, ARA_MAP_S3_REGION,
ARA_MAP_S3_PREFIJO, ARA_MAP_S3_ROLE_ARN. No long-lived access keys.

6. RESTORE POLICY (agreed position for B's verifier)
- Database and bucket restored to one point into a fresh isolated target.
- Every referenced final key must exist with the recorded size and SHA-256; any missing or
  inconsistent object fails acceptance. Active geometry links are checked the same way.
- Sessions: team_session and team_login_failure are emptied; everyone signs in again.
- Leases: archivo_trabajo is not restored (already excluded from backups by design).
  Versions restored in "subiendo" are left to end by their existing deadlines; their staging
  is not restored and they are reported, not repaired.
- Unreferenced objects are reported only.
