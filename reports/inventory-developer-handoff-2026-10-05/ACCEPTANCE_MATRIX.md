# Inventory release: independent acceptance matrix

Prepared October 5, 2026 for the supervisor and AI developers. This document specifies verification work; it does **not** certify that the new inventory exists or that any tests passed today. Application code, tests, credentials and production data were not changed for this assignment. The agreed product direction is in `reports/product-plan-2026-10-05/SUPERVISOR_PLAN.md`; the supervisor's handoff controls sequencing and any scope adjustments.

Reconciled to `INTEGRATION_DECISIONS.md` contract v1. That document's DTOs, route allowlist, validation rules and mutation semantics control these tests. Published data comes from the immutable revision selected by the published pointer and a shared explicit serializer; no separate publication table is required.

## 1. Evidence baseline and known boundaries

Fresh source inspection, not runtime verification:

- `server/app.py` registers legacy bases, maps, folders, imports and export routes. Its loopback handler is not the cloud authentication boundary. Passing local browser smoke alone cannot establish public/private separation.
- `api/index.py` currently permits general anonymous GET requests, restricts import/format routes, and explicitly exempts `/api/exportar` from the signed-in requirement. These are review targets when introducing publication; do not preserve unrestricted legacy reads by accident.
- `server/cloud_auth.py` currently implements a shared password, signed expiry token and optional `ARA_MAP_PUBLIC_EDIT` bypass. It does not establish individual actors. The new identity design must remove or safely disable that bypass in deployed operation; no staff role hierarchy is required.
- `server/db.py` currently reports schema version 7; `terreno` belongs to a base, while `mapa_terreno` preserves snapshots. `server/postgres.py` maintains explicit backup table lists. New inventory, revision, actor and history tables must participate in the documented recovery strategy.
- `server/api/exportar.py` exports requested base/map rows and uses a fixed column list. The new contract makes all legacy exports authenticated-only; current omission of contacts from columns does not make that route public.
- `tests/test_cloud.py` uses an HTTP server around the cloud handler; many ordinary API tests call Python handlers directly. Both levels are needed. Existing tests are starting points, not evidence of coverage for new publication and individual accounts.

Historical evidence only: `reports/readiness-2026-09-30/READINESS_REPORT.md` recorded mobile search/filter and import edge-case findings. `reports/urgent-usd-import-2026-10-01/release/LIVE_CONFIRMATION.md` later confirmed the specified 79-row USD workbook and saved map in production. Neither report proves today's candidate or broader import reliability. Reproduce relevant cases before calling them open or fixed. Do not reuse their pass counts as this release's results.

## 2. Disposable environment and evidence rules

1. Record candidate commit, dirty-file manifest/diff, runtime versions, schema versions and test fixture hash. All evidence must identify the same candidate or explain an intervening change.
2. Use fictional fixtures. Give every confidential field a unique sentinel, including contact, notes, arbitrary imported columns, source filenames and actor metadata. Include sentinels inside existing snapshots and import drafts.
3. Start SQLite with a newly created temporary directory and `ARA_MAP_DB` pointing inside it. Remove `DATABASE_URL`, `ARA_MAP_DATABASE_URL` and `ARA_MAP_TEST_DATABASE_URL` from the process environment unless explicitly running the disposable Postgres stage. Do not rely on an unqualified default database path.
4. Postgres tests require an explicitly provisioned **disposable** local database (UTF-8) or already-authorized test environment. `ARA_MAP_TEST_DATABASE_URL` alone is not proof the target is disposable. Verify target ownership/type without printing credentials; refuse production. Existing `tests/test_postgres.py` and `tests/test_postgres_aceptacion.py` use unique schemas and drop them, and the latter truncates tables; schema isolation does not authorize pointing them at production.
5. Exercise both adapters' shared authentication policy, including the real cloud adapter against disposable Postgres, using three distinct accounts/browser contexts plus an anonymous context. Use the contract's documented loopback-only cookie configuration for isolated browser tests; separately assert production Secure-cookie attributes. A local HTTPS harness may exercise those attributes end to end. Do not weaken production settings or use `ARA_MAP_PUBLIC_EDIT=1` as a substitute for authentication.
6. `tests/e2e/smoke.mjs` provisions and deletes data. Run it only against the disposable target, never the live URL. Adapt the authenticated flows for the changed product rather than bypassing the boundary. Use supported browser automation, record desktop and phone screenshots, console/network errors and assertion logs.
7. No production writes, imports, publish actions, deployment, credentials discovery or paid services are part of this packet. Live release checks occur only under the supervisor's separate concrete release instruction. Sanitize HAR/logs so they contain no session cookies, passwords or real internal records.

## 3. Representative dataset

Create at least **120 master terrains** to test beyond the 100-record baseline: initially 100 published available records, 10 drafts and 10 unpublished records. Use a manifest of stable IDs and expected values; transition selected records during scenarios rather than assuming counts remain constant.

Add a separate **251 matching published-record** fixture to cross the maximum 250-row page boundary. Verify default 100-row and maximum 250-row pagination, full facets and complete map/table assembly. This fixture supplements the business baseline; it is not a storage cap.

Distribute fictional records across several states and municipalities, with accented names, repeated names for distinct locations, nearby parcels, area extremes, MXN and USD, exact unit-price cents, total/per-m² prices, unknown values, fresh/stale/never-confirmed dates and valid coordinates. Include invalid or missing coordinates, missing prices and incomplete records in drafts. Test which cases may publish against the agreed field contract, not a verifier-invented mandatory-field list. Include HTML-like text and Excel-formula-like strings as literal data.

Separately include legacy base versions, genuine duplicate candidates, demonstration records and saved maps/comparisons. Add a workbook of over 100 rows, multiple sheets and over 12 exclusions to exercise historical review limits. Keep legacy records distinct from the 120 expected master records until explicit migration decisions link them.

## 4. Required behavioral matrix

## 5. Independent public-route leakage audit

The verifier enumerates the **final** route registry and both adapters rather than using only the developer's claimed route list. The public API allowlist is exactly GET `/api/config`, GET `/api/session`, POST `/api/login`, POST `/api/logout`, GET `/api/publico/terrenos`, and GET `/api/publico/terrenos/:id`. Static assets remain public. All other APIs require authentication, including unknown-route/fallback paths. For every method record: anonymous status, allowed public keys, membership rule and authenticated behavior.

Audit legacy `/api/bases`, `/api/bases/:id`, `/api/bases/:id/terrenos`, `/api/mapas`, `/api/mapas/:id`, `/api/mapas/:id/terrenos`, `/api/carpetas`, `/api/formatos`, all `/api/importar/*`, and `POST /api/exportar`. Every legacy workspace route requires sign-in; an alternative public projection on these paths is not permitted. Anonymous requests return 401 with no internal payload. Do not expose base/map/folder names, counts, raw `extra_json`, findings, metadata or snapshots merely because a path uses GET. Preserve internal historic snapshots behind authentication.

Submit known/guessed draft IDs, unpublished IDs, old map IDs, source IDs and mixed published/private export IDs. Try omitted `ids` (currently “all”), empty `ids`, selection filters and map-layer exports. All anonymous exports must fail; no public export action appears. Authenticated exports retain correct sheet/selection/currency behavior. Inspect JSON, HTML, error text, browser preload/cache/local storage and any downloaded files. Public detail returns 404 for nonpublic IDs without distinguishing private existence.

Sentinel scan must return **zero occurrences** in every anonymous response/file, but also assert the exact `PublicTerrain` allowlist in `INTEGRATION_DECISIONS.md`: missing sentinels alone does not prove safety. After logout/back navigation, pending drafts and private details must not remain rendered or recoverable from the app's retained client state. Public GETs started after withdrawal commit must not return the old listing; focus/reload revalidation updates already open pages. Publication must never mutate historical internal snapshots merely to sanitize public reads.

## 8. Release gates and reporting

| Gate | Supervisor accepts only when |
|---|---|
| G0: contract | Public field allowlist, revision/conflict semantics, identity provisioning, migration mapping and publication validation are explicit. Attention starts with missing/never-confirmed information; no business staleness cutoff is invented. |
| G1: development integration | Core matrix passes on isolated SQLite where supported and real disposable Postgres. New individual-account and cloud-HTTP tests pass. No role-management UI or shared-login substitution. |
| G2: independent verification | Separate verifier executes full user journeys, legacy-route leakage audit, three-session concurrency and migration/recovery rehearsal; all release-blocking defects are fixed/retested. Include evidence for the exact candidate. |
| G3: pilot readiness | 100+ published records are navigable with three signed-in sessions. An employee completes create → edit → preview → publish → confirm availability → unpublish unaided; boss/public browsing succeeds on desktop/phone. Real data disposition is reviewed. |
| G4: authorized release | Supervisor reviews deployment/recovery packet and separately authorizes concrete deployment/data migration. Afterwards verify the deployed candidate, public filtering/cache behavior and actual persistence under the authorized live-check scope. |

Performance diagnostics: with 120 master records and the separate 251-record pagination case, measure public inventory time-to-interactive, filter feedback and save/publish duration (p50/p95 across at least 30 actions), recording device, network, environment, cold/warm distinction and map-tile latency. Initial diagnostic flags may use 3 seconds warm / 5 seconds cold for browsing, 500 ms for filter feedback and 2 seconds warm p95 for save/publish; these are not release gates or customer promises. Establish the measured baseline before the supervisor agrees performance budgets. Publication consistency is a separate correctness requirement: a public GET started after successful commit reflects the committed state, with no five-second grace period. Three editor sessions establish only the agreed small-team workload, not capacity for unspecified public traffic.

Locally provable: validation, storage transitions, deterministic conflict handling, public projection through the real adapter, legacy endpoint access policy, migration/recovery on representative data and UI workflows in measured local conditions. Live-only proof after authorization: actual release identity, provider cookie/domain behavior, production environment configuration, deployment cache freshness, real cloud cold-start/load timings and reconciliation of the actual migrated dataset. State “not verified live” until that work occurs.

Final verifier report must list candidate/environment, matrix pass/fail/skip IDs, evidence paths, dataset counts, migration reconciliation, recovery outcome, measured timings, remaining limitations and a GO/NO-GO recommendation. Any unauthorized disclosure, silent data loss/overwrite, accidental publication, failed recovery, or essential unreachable phone control is release-blocking. Supervisor—not developer self-report—makes the final readiness decision.
